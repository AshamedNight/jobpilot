# 手机端：调试方法与选择器清单

> 面向要改这个 App 的人。BOSS 一次改版就可能让下面某些 id 失效，
> 本文的作用是让你**在 10 分钟内重新校准**，而不是重新摸索一遍。

---

## 一、App 更新后，第一步永远是重新抓 dump

App 里留了两个调试按钮（首页「调试工具」区）：

| 按钮 | 作用 |
|---|---|
| 抓取界面 | 把当前屏幕的无障碍节点树导出成文本 |
| 复制结果 | 复制到剪贴板，粘到记事本发出来 |

**关键点：抓取必须发生在 BOSS 是前台窗口的时候。**

因为无障碍服务读的是 `rootInActiveWindow`——你切回 JobPilot 的那一刻，
前台窗口已经变成 JobPilot 自己了，这时点「抓取界面」拿到的是我们自己的页面。

所以服务做了**缓存**：在 BOSS 前台时由无障碍事件触发、节流 1.5 秒把节点树存进内存，
主界面点「抓取界面」拿的是那份缓存。状态栏会标注「实时」还是「缓存于 N 分钟前」。

## 二、两次抓取，缺一不可

| 抓哪里 | 存成 | 用来确认 |
|---|---|---|
| BOSS 搜索结果列表页 | `dump.txt` | 岗位卡片容器、职位名、公司名 |
| 任一职位详情页 | `dump-detail.txt` | 底部主按钮（能不能发）、返回按钮 |

## 三、选择器清单（2026-11-14 真机实测）

### 列表页

```
RecyclerView #recyclerView_list                     ← 岗位列表（唯一数据源）
└─ LinearLayout [bounds] click                      ← 一个岗位卡片（外层无 id）
   └─ ViewGroup #cl_card_container
      └─ FrameLayout #boss_job_card_view
         └─ ViewGroup #view_job_card
            ├─ #tv_position_name     职位名
            ├─ #tv_salary_statue     薪资
            ├─ #tv_company_name      公司名
            ├─ #tv_scale             公司规模
            ├─ #tvIndustryName       行业
            ├─ #tv_digest            JD 摘要（可能被截断）
            ├─ #tv_employer          "姓名 · 头衔"
            ├─ #tv_distance          地区
            └─ #iv_improper  click   ⚠️ 举报按钮
```

### 详情页

```
FrameLayout #title_action_view
├─ ImageView #iv_back                               返回
└─ LinearLayout #ll_title → TextView #tv_title      职位名

FrameLayout #bottom_action_view
└─ ViewGroup #cl_geek_action
   └─ Button #btn_chat  "立即沟通" / "继续沟通"   ← 核心判据
```

**`#btn_chat` 一个 id 同时解决两件事**：
- 文字含「立即」= 没打过，可以发
- 文字含「继续」= 已经打过，跳过

## 四、五个已知的坑（改代码前务必看）

1. **列表页没有「已沟通」标记**。整个卡片是一块可点区域，必须进详情页才知道打没打过。
2. **最后一张卡片是半截的**（后代节点全 `hidden`）。必须过滤
   `card.bounds.bottom <= list.bounds.bottom`，否则会点歪到 `#iv_improper`——那是举报。
3. **坐标可能带巨大偏移**（实测见过 `+857`）。用户开分屏时 BOSS 在右半边。
   **不要用绝对坐标做任何判断**，只用节点自身的 bounds 相对计算。
4. **`#recyclerview_filter_new` / `#recyclerView_lable_filter` 也是 RecyclerView**，
   但那是筛选标签，不是岗位列表。认准 `#recyclerView_list`（大小写不同）。
5. **点「立即沟通」之后界面未知**。可能直接发出（账号自带招呼语），
   也可能弹输入框。代码里的处理是**运行时判断**：
   有新出现的输入框 → 填文案 + 找「发送」；没有 → 当作已发出。

## 五、安全约束（不要为了"跑得快"拆掉）

| 约束 | 原因 |
|---|---|
| 只操作 `packageName == com.hpbr.bosszhipin` 的窗口 | 否则切回本 App 时，会把我们自己的页面当"陌生界面"一路按返回，把 App 退出 |
| 每 tick 重新判断当前是哪一屏 | 被弹窗打断、被人手点一下，下一秒能自己找回来；记"第几步"的状态机做不到 |
| 间隔 60–150 秒随机 + 每 3–5 条长休 | 连续动作是平台最容易识别的特征 |
| 见到「操作频繁 / 稍后再试 / 系统繁忙」立即停 | 硬试只会把一次限流变成一次标记 |
| 连续翻 4 屏无新岗位就停 | 到底了还一直划，既浪费动作也没意义 |

## 六、改完怎么验证（不需要完整跑一遍）

1. 装新 APK
2. 开无障碍 → 在 BOSS 里搜「法务」→ 切回来点「开始打招呼」
3. **只盯前 1 条**：状态行应从「点开：XXX」→「底部按钮：立即沟通」→「已发送 · 今日 1/50」
4. 若停在某一步，立刻点「暂停」，把那一步的状态文字和当前屏幕记下来

## 七、分屏 / 小窗：不要用 `rootInActiveWindow` 判断"BOSS 在不在"

**这是 v0.2.0 真机第一次跑就踩到的坑**，值得单独写一节。

现象：用户开着分屏（JobPilot 一半、BOSS 一半），BOSS 明明就在屏幕上、列表也正常显示，
但点「开始打招呼」后一直提示「请切到 BOSS 界面」，两次测试都一样。

原因：`rootInActiveWindow` 返回的是**当前活动窗口**。用户刚点过 JobPilot，
活动窗口就是 JobPilot，哪怕 BOSS 就在旁边可见。

正确做法（`BossAccessibilityService.bossRoot()`）：

```
1. 先看 rootInActiveWindow 是不是 BOSS —— 是就直接用（最常见、零成本）
2. 不是则遍历 windows（需要 flagRetrieveInteractiveWindows），按包名找 BOSS 窗口的 root
3. 都找不到才算"BOSS 不在"
```

配套的两个改动：

- **`swipeUp()` 用 BOSS 窗口的 bounds 算坐标**，不是整屏。分屏时 BOSS 只占半屏，
  用整屏坐标划会划到 JobPilot 那头去。
- **点「开始」时如果 BOSS 不在，自动 `startActivity` 拉起它**（MainActivity 一次 + 引擎兜底 2 次）。
  只拉有限次：反复拉起会一直打断用户，看起来像程序疯了。

**副作用（必须接受）**：BOSS 必须在屏幕上才能工作——无障碍读的就是 BOSS 的界面。
用户切回 JobPilot 看进度时引擎会暂停等待（不会误点），切回去继续。
所以"看进度"和"保持 BOSS 在前台"天然冲突，这一点只能靠通知栏解决，不是 bug。
